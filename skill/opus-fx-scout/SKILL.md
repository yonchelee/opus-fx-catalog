# opus-fx-scout

사람들이 Claude에 프롬프트를 주고 실제로 만들어낸 효과들의 카탈로그를 근거로,
"내 결과물에 쓸 만한 효과"를 골라주고 그걸 만들 준비가 됐는지 확인해 주는 스킬입니다.
감으로 효과를 추천하는 대신, 실제로 만들어진 사례와 원본 프롬프트를 근거로 삼는 것이 이 스킬의 가치입니다.

## 파일

- `scripts/find.py` — 카탈로그 검색. `--show <id>`로 전문, `--stats`로 효과별 개수
- `scripts/sync.py` — 등록된 소스에서 새 항목을 받아 분류 (`--dry-run`, `--add`, `--register`)
- `scripts/classify.py` — 효과(16종)와 필요 도구(level 1~4) 분류 규칙
- `references/tooling.md` — 필요 도구 확인표 작성법, 플러그인 찾는 법. **추천을 낼 때 읽기**
- `references/discovery.md` — 새 소스 발굴 절차. **자가서칭 모드에서 읽기**
- `data/catalog.json` — 스냅샷, `data/sources.json` — 등록된 소스
- 공유 저장소 `yonchelee/opus-fx-catalog` — 주간 업데이트가 쌓이는 카탈로그. 스크립트가 자동으로 읽어 스냅샷 위에 합칩니다

스크립트는 이 스킬 폴더 기준 경로로 실행합니다 (예: `python3 <skill>/scripts/find.py ...`).

## 모드 고르기

- **추천 모드**: 사용자가 무언가를 만들려고 함 → 아래 "추천 절차"
- **자가서칭 모드**: "새 효과", "업데이트", "/효과업데이트", 또는 예약 작업으로 호출됨 → `references/discovery.md`
- 둘 다일 수 있습니다. 예: "요즘 새로 나온 것 중에 내 전시에 쓸 만한 거" → 자가서칭 후 추천

## 추천 절차

### 1. 결과물 파악
알아야 할 것: 무엇을 만드는지(주제·내용), 결과물 형태(MP4 영상 / 웹페이지 / 인터랙티브 / SNS 클립), 길이·비율, 가진 자료(사진·로고·음악·데이터), 원하는 분위기, 쓸 수 있는 환경(채팅만 / Claude Code).
대화에 이미 있으면 다시 묻지 않습니다. 결과물 형태처럼 추천이 크게 갈리는 것이 비어 있을 때만 한 번 묶어서 묻고, 나머지는 합리적으로 가정한 뒤 가정을 밝힙니다.

### 2. 카탈로그 동기화 (가볍게)
`python3 scripts/sync.py`를 한 번 돌립니다(추천 모드에서는 `--out` 없이, 저장소 커밋은 자가서칭 모드에서). 실패해도 멈추지 말고, `find.py --stats` 첫 줄의 카탈로그 기준 날짜를 답변 끝에 밝힙니다.

### 3. 후보 찾기
카탈로그 프롬프트는 대부분 영어이므로 결과물의 핵심을 영어 키워드로 옮깁니다.
주제 키워드(building, archive, product, map ...). "photo", "film", "video"처럼 어디에나 나오는 단어는 순위를 흐리므로 피하고,와 연출 키워드(watercolor, scroll, parallax, typography ...)를 섞어
`find.py`를 2~3번, 다른 각도로 돌립니다. 예:

```bash
python3 scripts/find.py --kw archive historic building street map --any-fx 3d paint data --top 15
python3 scripts/find.py --kw scroll parallax typography --any-fx kinetic morph --max-level 2 --full
```

점수는 대략적인 1차 거름망일 뿐입니다. 미리보기로 명백히 엉뚱한 것은 넘기고, 남은 후보(보통 5~10개)는 `--show`로 **전문을 직접 읽고** 고르세요.
분류 키워드가 맞아도 내용이 엉뚱한 경우가 있고, 키워드가 없어도 연출 기법이 딱 맞는 경우가 있습니다.

### 4. 3개 고르기
고르는 기준, 중요한 순서대로:
1. **결과물의 목적에 효과가 봉사하는가.** 아카이브라면 정보가 읽혀야 하고, 런칭 영상이라면 첫 1초 훅이 중요합니다. 화려하지만 내용을 가리는 효과는 뺍니다.
2. **배울 게 있는 프롬프트인가.** 전문이 공개되고 구체적인 기법(타이밍, 카메라, 렌더 방식)이 적힌 것이 좋습니다. "쇼릴처럼 다 보여줘" 한 줄짜리나 [일부 공개]는 연출 참고로만 쓰고, 그렇다고 밝힙니다.
3. **사용자 환경에서 만들 수 있는가.** 가능하면 level이 낮은 것을 우선하고, level이 높으면 낮출 대안을 함께 제시합니다.
4. **서로 다른 접근일 것.** 비슷한 3개보다 방향이 다른 3개가 선택에 도움이 됩니다.

맞는 게 3개가 안 되면 억지로 채우지 말고 있는 만큼만 냅니다. 하나도 없으면 없다고 말하고, 가장 가까운 것과 무엇이 다른지 설명합니다.

### 5. 제안하기
`references/tooling.md`를 읽고, 아래 형식으로 작성합니다.

~~~
### ① [한 줄 제목 — 결과물에 적용했을 때의 모습]
**원본**: @작성자 — 원본 요지 한 줄 · [게시물](post_url) · [영상](video_url) · [프롬프트 원문](prompt_url)
**왜 이 결과물에 효과적인가**: 2~3문장. 원본의 어떤 기법이 사용자 결과물의 어떤 문제를 푸는지.
**응용 프롬프트** (한국어, 바로 붙여 넣을 수 있게)
```text
...
```
**만들려면 필요한 것** · 실행 단계: ○○
| 필요한 것 | 왜 | 지금 환경 | 준비 방법 |
~~~

응용 프롬프트를 쓸 때:
- 원본의 **구조적 기법**(타이밍 설계, 렌더 파이프라인, 검증 단계, 금지 목록)은 살리고, 주제와 소재를 사용자 것으로 바꿉니다. 원본 프롬프트를 그대로 번역만 하는 건 응용이 아닙니다.
- 사용자 자료가 들어갈 자리는 `[대괄호]`로 남깁니다.
- 사실(연도, 건물명, 제품 정보)은 확인한 것만 쓰고, 확인 못 한 건 확인 필요라고 표시하거나 사용자 자료로 대체하게 합니다.
- 특정 작가의 화풍을 베끼라고 하지 말고 화풍의 특징을 묘사합니다.

마지막에 **한 번만** 묻습니다: 어떤 것으로 진행할지, 필요한 도구 중 이미 있는 것과 설치해도 되는 것.
설치·유료 API 호출·외부 게시는 사용자가 확인하기 전에 하지 않습니다.

### 6. 확인 후
사용자가 고르면, 지금 환경에서 가능한 범위에서 바로 만들거나(채팅이면 HTML 아티팩트, Claude Code면 프로젝트),
환경이 안 맞으면 어디서 무엇을 실행하면 되는지 안내합니다.
짧은 MP4 클립이나 설명 영상처럼 전용 제작 스킬(HyperFrames 등)이 더 잘 만드는 결과물이면, `references/tooling.md` 5절대로 그 스킬에 응용 프롬프트를 브리프로 넘기는 길도 함께 제시합니다.

## 정직하게 알려야 할 것
추천과 함께, 해당되는 것만 짧게 언급합니다.
- Claude는 영상을 직접 그리지 않고 코드를 짜서 렌더링합니다. 채팅에서는 HTML이 나오고, MP4는 Claude Code 같은 실행 환경이 필요합니다.
- level 4 작품의 실사·캐릭터·음성은 외부 생성 AI가 만든 것입니다.
- 카탈로그는 잘 나온 결과만 모인 것이라 같은 프롬프트로도 몇 번 다시 시켜야 할 수 있습니다.
- 모든 원본의 권리는 각 작성자에게 있습니다. Li-Evan 소스(src가 lievan) 항목은 CC BY 4.0이라 다시 공개할 때 출처 표기가 필요합니다. 응용해서 공개할 때는 영감을 준 원본을 밝히길 권합니다.
